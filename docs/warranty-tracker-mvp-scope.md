# MVP Scope Document — WarrantyKeeper

**גרסה:** 1.0 | **תאריך:** ספטמבר 2026
**מטרה:** לגזור מה-PRD המלא רשימה מינימלית וריאלית שניתן לבנות תוך 4-6 שבועות, ושעדיין מספקת ערך אמיתי לבדיקת Product-Market Fit.

---

## 1. עיקרון מנחה

MVP טוב עונה על שאלה אחת: **"האם אנשים יטרחו לצלם קבלה ולחזור לאפליקציה כשמוצר מתקלקל?"**
כל פיצ'ר שלא משרת ישירות את השאלה הזו — נדחה ל-V1.5/V2, גם אם הוא נחמד.

---

## 2. בפנים (In Scope) — מה שכן נבנה

| פיצ'ר | הערה |
|---|---|
| הרשמה בסיסית (מייל + סיסמה, או Google OAuth) | לא צריך יותר משיטת התחברות אחת ב-MVP |
| צילום קבלה + OCR | ליבת הערך המוצע — חובה |
| אישור/עריכה ידנית של נתונים שזוהו | חובה — OCR לא יהיה מדויק ב-100% |
| מאגר warranty_rules מצומצם (~30 קטגוריות נפוצות בלבד) | די כדי לכסות רוב המקרים הנפוצים בבית |
| Dashboard עם מיון לפי "קרוב לתפוגה" | המסך המרכזי שיוצר חזרתיות שימוש |
| מסך מוצר בודד עם סטטוס אחריות | ליבת הערך בזמן אמת |
| כפתור "המוצר התקלקל" עם פרטי קשר יצרן סטטיים | לא צריך טופס דינמי מורכב — טקסט/טלפון/קישור מספיקים |
| התראת פוש בודדת (30 יום לפני תפוגה) | להוכיח את ערך ההתראות בלי לבנות מערכת תזמון מורכבת |
| חיפוש טקסט פשוט | לא צריך סינון מתקדם עדיין |
| household עם עד 2 משתמשים (בלי הרשאות מורכבות) | שיתוף בסיסי בין בני זוג, לא ניהול הרשאות מלא |

## 3. בחוץ (Out of Scope ל-V1) — נדחה במפורש

| פיצ'ר | למה נדחה |
|---|---|
| אינטגרציית מייל אוטומטית (Gmail) | מורכבות טכנית ופרטיות גבוהה, לא הכרחי להוכחת הקונספט |
| Web Dashboard | המובייל מספיק להוכחת ערך; Web מוסיף עומס פיתוח כפול |
| מודל Premium/תשלום | לבדוק ערך חינמי לפני מונטיזציה |
| ריבוי רמות התראה (30/14/3 ימים, סיכום שנתי) | מתחילים עם התראה אחת, מרחיבים אם יש ביקוש |
| מרקטפלייס תיקונים / קהילת ביקורות | פיצ'רים של שלב מאוחר בהרבה, תלויים בבסיס משתמשים קיים |
| B2B / ניהול נכסים מרובים | שוק נפרד, לא לבדוק יחד עם ה-B2C הראשוני |
| הרשאות משק בית מתקדמות (צפייה/עריכה נפרדות) | לא קריטי עם 2 משתמשים בלבד |
| ייצוא לביטוח | תלוי בבסיס נתונים בוגר יותר, לא רלוונטי ביום הראשון |
| קטגוריזציה אוטומטית מלאה (NLP) | ב-MVP: זיהוי מבוסס מילות מפתח פשוט בלבד, לא מודל שלם |

## 4. קריטריון הצלחה ל-MVP (Exit Criteria)

ה-MVP נחשב "מוצלח" אם, אחרי 6-8 שבועות בשוק עם קבוצת משתמשים ראשונית (50-100 בטא):

1. לפחות 40% מהמשתמשים חוזרים לאפליקציה שנייה פעם תוך שבועיים מההרשמה.
2. ממוצע 5+ מוצרים נוספים למשתמש פעיל.
3. לפחות 3-5 מקרים מתועדים שבהם משתמש לחץ "המוצר התקלקל" ודיווח בחזרה (בסקר קצר) שהמידע היה שימושי.
4. משוב איכותני (ראיונות קצרים) שמאשש שהכאב שזיהינו אכן קיים ושהפתרון מוריד אותו.

אם הקריטריונים לא מתקיימים — עוצרים לפני השקעה נוספת ובוחנים מחדש הנחות יסוד (ולא רק מוסיפים פיצ'רים).

---

## 5. הערכת זמנים ריאלית (4-6 שבועות)

| שבוע | משימה |
|---|---|
| 1 | סטאפ פרויקט (API + DB schema + מובייל בסיסי), אימות/הרשמה |
| 2 | זרימת צילום קבלה → OCR → מסך אישור נתונים |
| 3 | בניית מאגר warranty_rules ראשוני (~30 קטגוריות), חישוב תאריך תפוגה |
| 4 | Dashboard + מסך מוצר בודד + חיפוש בסיסי |
| 5 | כפתור תביעת אחריות (סטטי) + התראת פוש בודדת + household בסיסי |
| 6 | בדיקות, תיקון באגים, הכנה להשקה עם קבוצת בטא |

---

## 6. סיכון עיקרי ב-MVP המצומצם

הצמצום המשמעותי ביותר הוא **מאגר warranty_rules חלקי** — ייתכן שמוצרים רבים לא יקבלו התאמה מדויקת בהתחלה. זהו סיכון מקובל ל-MVP: המטרה היא לבדוק את ההרגל וההתנהגות (צילום קבלה, חזרה לבדיקת סטטוס), לא לכסות 100% מהמקרים מהיום הראשון. חשוב לתקשר זאת בבירור למשתמשי הבטא ("הרשימה שלנו עדיין גדלה").
